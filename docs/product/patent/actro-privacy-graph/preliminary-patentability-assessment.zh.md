# Actro 动态隐私图闭环：专利性初步检索与评估

- 版本：0.1
- 检索日期：2026-07-30
- 评估对象：Actr Actor 网络、Actro 应用宿主与运行时隐私状态机制
- 主要法域视角：中国发明专利，并兼顾 PCT、美国和欧洲申请

> 本报告是产品与技术团队用于决定是否进入正式专利工作的初步材料，不是法律意见，也不是完整的新颖性检索、无效检索或自由实施（FTO）意见。最终申请范围、发明人、公开日和法域策略应由专利代理师或律师确认。

> 术语说明：本报告写于 2026-07-30，沿用当时的实施例命名。现行安全模型（[docs/security](../../../architecture/security/actrium/README.zh.md)）已改用以下对应对象，语义映射为：`PrivacyGraphRoot` ≈ `structureDigest`；`GraphEpoch` ≈ `ApplicationStateDigest`（结构 + 各节点当前状态根的承诺）；「旧 Epoch 能力冻结」对应「`ActorStateDigest` 含单调修订号，状态变化持久废除旧绑定（内容回滚不复活）」。报告中的机制分析不受命名差异影响；正式申请文件撰写时应以现行模型词汇为准。

## 一、结论摘要

### 1. 是否值得申请

**值得，但不能以“综合多路安全技术并给应用显示绿标或黄标”作为核心发明。**

这一宽泛表述覆盖的各个部分——组件图、最弱项聚合、多维可信状态、远程证明、证明后授权或密钥释放、状态变化后重新评估、权限增加时暂停并征求同意、Epoch 与短期租约——都已经分别存在成熟标准、产品机制或专利。把它们并列拼装，容易被审查员认定为已知技术的简单聚合。

目前最值得申请的核心是一个更窄、更技术化的协议：

> **在运行中应用的 Actor 隐私图发生候选变化时，在新节点或新边获得业务数据之前，原子冻结旧图的数据平面及其旧 Epoch 能力；保留一个类型受限且不能承载业务明文的控制平面；对候选图生成并评估证明；仅在隐私保障向量发生降级或不可比时要求用户授权；最终把新的通信密钥、数据能力和授权绑定到候选图根与新 Epoch 后再恢复业务通信。**

本轮检索没有发现一项单独资料完整公开上述全部步骤及其并发安全约束。因此，它可以作为后续正式检索和权利要求撰写的主攻方向。

## 二、拟解决的技术问题

申请文件不宜把技术问题写成“如何让用户理解应用是否安全”或“如何认证一款应用”。这容易落入信息展示、管理规则或抽象评价。

建议将技术问题表述为：

1. 动态分布式应用在增加、替换或重连计算节点时，怎样防止未经评估的新节点在评估完成前收到敏感业务数据；
2. 怎样防止旧图的证明结果、用户授权、会话密钥或能力令牌在图发生变化后被重放；
3. 怎样在暂停业务数据的同时保留证明、协商和授权所必需的活性，又不让该控制通道成为业务数据旁路；
4. 怎样在安全性未下降时自动完成迁移，而只在安全保障实际下降或不可比较时中断用户；
5. 怎样在并发图变化、消息在途、证明过期、节点故障和恢复等情况下，保证“先冻结、后评估、再生效”的线性化顺序。

对应的技术效果应当能够测试：

- 候选边在提交前可发送的业务载荷字节数恒为零；
- 旧 Epoch 的能力、消息和密钥在迁移提交后被确定性拒绝；
- 控制平面的消息类型、大小、速率和字段受协议约束，不能承载业务载荷；
- 相同或更强的候选图无须重新征求用户同意即可恢复；
- 降级授权不能被重放到其他应用实例、图根、Epoch、数据类别或策略版本；
- 崩溃恢复后不会同时存在两个可承载业务数据的有效图 Epoch。

## 三、推荐的发明定义

### 1. 推荐名称

首选：

> 一种基于运行时组件图版本的隐私数据平面原子迁移控制方法、系统、设备及存储介质

备选：

> 一种动态 Actor 应用的隐私图迁移与图绑定能力控制方法

独立权利要求宜使用“运行时组件”“分布式执行单元”或“消息处理单元”等较宽术语，在说明书中把 Actor、Actr 和 Actro 作为优选实施例，避免无必要地把保护范围限死在产品名称或浏览器形态上。

### 2. 核心状态机

```text
ACCEPTED(GraphRoot=e.root, Epoch=e)
  │
  ├─ 拦截到隐私语义变化意图
  ▼
FREEZING
  - 关闭旧 Epoch 的业务数据许可
  - 阻止候选边和候选节点取得业务密钥/能力
  - 仅开放受限控制平面
  ▼
EVALUATING(CandidateRoot, CandidateEpoch)
  - 收集/验证证明
  - 生成候选保障向量
  - 与已接受基线作偏序比较
  │
  ├─ 各必需维度均不下降且策略通过
  │      └─ COMMIT：换密钥、发新能力、恢复业务
  │
  ├─ 存在下降或不可比
  │      └─ PENDING_CONSENT
  │             ├─ 获得候选图绑定授权 → COMMIT_YELLOW
  │             └─ 拒绝/超时 → ABORT 或保持冻结
  │
  └─ 触发不可覆盖的硬性下限
         └─ ABORT，无用户越权通道
```

### 3. 建议写入独立权利要求的必要组合

以下特征应作为一个相互作用的组合，而不是互不相关的清单：

1. 保存已接受应用实例的运行时组件图快照、图标识或图根、当前图 Epoch，以及已接受的多维隐私保障基线；
2. 使业务数据平面的通信能力、数据密钥或短期许可至少绑定应用实例标识、图 Epoch、通信边和数据类别；
3. 在候选节点或候选边生效前，由宿主或数据平面闸门拦截会改变隐私语义的图变更意图；
4. 将旧 Epoch 切换到冻结状态，使旧许可不能继续授权业务载荷，同时阻止候选图取得业务数据许可；
5. 冻结期间仅允许独立定义的控制消息集合，用于发现、证明、策略评估和授权，且该集合不能携带业务载荷；
6. 构建候选图并验证各节点、边、宿主和执行环境的证据，得到候选多维保障状态；
7. 用偏序而非单一总分比较候选状态与已接受基线：
   - 所有必需维度均不下降且满足策略时，自动接受；
   - 任一必需维度下降或不可比较时，保持业务冻结并生成精确降级差异；
8. 自动接受时，提交候选图为新 Epoch，重新派生或发放图绑定密钥/能力，并恢复数据平面；
9. 降级时，仅在收到绑定到应用实例、候选图标识、候选 Epoch、具体降级维度、受影响数据类别、策略摘要和有效期的授权对象后恢复，且恢复状态不能标为绿色；
10. 对硬性策略失败禁止用户覆盖；
11. 保证图变更拦截、旧 Epoch 冻结、候选边激活和新 Epoch 提交之间满足线性化顺序，消除评估前的数据泄漏时间窗。

其中，第 3、4、5、8、9、11 项的联动，是相对现有技术最值得强调的部分。

说明书可公开但不必在最宽独立权利要求中写死如下字段：

这样可以把“安全结论”落实为实际控制通信和数据释放的密码学状态，而不是停留在 UI 标记。

## 四、最接近的现有技术

### 1. 风险聚合、阻止或提示用户

[US8156558B2，Mechanism for evaluating security risks](https://patents.google.com/patent/US8156558B2/en)，优先权日 2003-05-17：

- 使用多个风险评估器评价不同风险；
- 由信任管理器聚合结果；
- 根据结果加载、阻止或提示用户；
- 可针对具有多个组件和权限清单的应用作判断。

影响：宽泛的“汇聚多项安全技术后决定绿、黄、阻止或提示”已经非常接近现有技术。

### 2. 定义变化、缓存同意和重新授权

[US20190102525A1，Identifying and consenting to permissions for workflow and code execution](https://patents.google.com/patent/US20190102525A1/en)，优先权日 2017-10-02：

- 扫描工作流或代码定义并生成权限摘要；
- 缓存用户同意；
- 新摘要与原摘要一致时复用同意；
- 摘要不同时使缓存同意失效并重新提示。

影响：单独主张“图结构或权限摘要变化后重新征求同意”风险很高。Actro 需要依靠数据平面原子冻结、图 Epoch 和仅降级提示等更具体的协议差异。

### 3. 权限增强时先停用再提示

[Chrome 扩展权限警告机制](https://developer.chrome.com/docs/extensions/develop/concepts/permission-warnings)明确规定：扩展增加会触发警告的新权限时，可先被停用，直到用户接受新权限后才重新启用。

影响：“安全能力变弱/权限增加时暂停并征求用户同意”作为产品逻辑非常合理，但作为单独发明点较弱。Actro 的区别应是动态分布式 Actor 图、业务数据平面与控制平面分离、图绑定能力及原子迁移。

### 4. 状态改变后重新验证并调整网络访问

[US9436820B1，Controlling access to resources in a network](https://patents.google.com/patent/US9436820B1/en)，优先权日 2004-08-02：

- 周期或异步检测设备安全状态变化；
- 状态改变后触发完整的重新验证；
- 根据新状态降低、终止或提高资源访问；
- 不合规设备可进入隔离或修复网络，同时保留受限路径。

影响：“状态变化—重新评估—收紧或放宽访问—保留控制/修复路径”已有很早的披露。Actro 必须进一步限定图变更提交顺序、旧 Epoch 失效、候选边数据零泄漏和控制平面不可承载业务数据。

### 5. 组件依赖图、哈希和变化检测

[EP4182826B1，A method of attesting a state of a computing environment](https://patents.google.com/patent/EP4182826B1/en)，优先权日 2020-07-14：

- 用有向无环图表示运行组件及依赖关系；
- 对节点、依赖和子节点信息作哈希；
- 通过节点哈希变化发现组件或依赖被改变；
- 可在发现不安全组件时终止计算环境。

影响：图根、Merkle 化组件依赖和通过哈希发现图变化不能作为主创新。该专利族还需要在正式 FTO 中重点做权利要求比对。

### 6. 应用软硬件的多维证明图

[US20230274034A1，Method and apparatus for multi-dimensional attestation for a software application](https://patents.google.com/patent/US20230274034A1/en)，优先权日 2023-05-03：

- 证明图覆盖应用的软硬件组件及其关系；
- 图节点表示各组件证明，边表示空间或时间关系；
- 可覆盖微服务通信、依赖、执行栈和历史版本；
- 多个证明者可协作增量构建证明图。

影响：“应用由若干 Actor 构成，对所有 Actor 和依赖形成证明图”本身已很拥挤。应避免把“多维证明图”作为标题和唯一独立构思。

### 7. 动态运行时应用安全图

[US20240205259A1，Multi-layer application security graph for cloud-native applications using runtime telemetry](https://patents.google.com/patent/US20240205259A1/en)，优先权日 2022-12-20：

- 依据运行时遥测生成动态应用安全图；
- 覆盖微服务、第三方 API、数据存储、身份和数据出口；
- 用于分析攻击路径和展示风险。

影响：运行时动态图及安全可视化不是核心差异。

### 8. 远程证明后的服务网格通信

[US11399013B2，Secure service mesh](https://patents.google.com/patent/US11399013B2/en)，优先权日 2020-04-20：

- 安全 sidecar 对服务实例执行本地或远程证明；
- 证明成功后允许代理和通信；
- 证明过程产生的会话密钥用于保护服务实例与处理器标识。

影响：为每条 Actor 边执行证明后建立安全通信是已知方向。正式 FTO 应对其有效权利要求逐项比对。

### 9. 连续证明与编排事件

[US20220078015A1，Continuous integrity validation-based control plane communication in a container-orchestration system](https://patents.google.com/patent/US20220078015A1/en)披露了工作节点与控制平面的持续或事件触发完整性验证，并可由 Pod 创建、删除等事件触发重新验证。

影响：把“Actor 创建/删除触发证明”单独主张不强；应落到图迁移的事务和数据控制效果上。

### 10. 证明结果、策略和资源授权

[RFC 9334，RATS Architecture](https://www.rfc-editor.org/rfc/rfc9334.html)已经定义 Attester、Verifier、Relying Party、Evidence、Attestation Results、评估策略、信任锚和新鲜度；Relying Party 可依据证明结果作资源授权判断，标准还讨论时间、Nonce 和 Epoch ID。

[IETF AR4SI 早期草案](https://www.ietf.org/archive/id/draft-voit-rats-attestation-results-01.html)在 2021 年已描述 Trustworthiness Vector：由多个可信声明组成的向量，Relying Party 可据此允许或拒绝信息交换。

影响：异构厂商证明归一、可信验证者、证明向量、新鲜度和证明后授权宜直接兼容标准，不宜宣称为 Actro 独创。

### 11. 图或状态绑定的短期能力、租约与 Epoch

[US8990898B2，Connection leasing for hosted services](https://patents.google.com/patent/US8990898B2/en)公开了密码学签名的连接租约，租约可绑定客户端、主机、端口和资源，并支持到期、续租和撤销。

[WO2019022738A1，Managing entitlement](https://patents.google.com/patent/WO2019022738A1/en)公开了以 Epoch 版本管理授权凭证和撤销旧授权。

[US6775703B1，Lease based safety protocol for distributed system with multiple networks](https://patents.google.com/patent/US6775703B1/en)更早地披露了在新 Epoch 服务数据前重新确认锁、交换为当前 Epoch 的锁并使旧 Epoch 锁失效。

影响：Epoch、租约、轮换和旧能力失效是通用积木。主张重点必须是它们怎样与隐私图候选迁移、证明比较和无泄漏数据平面共同作用。

## 五、差异化与创造性判断

### 1. 尚未发现被单篇文献完整公开的组合

第一轮检索未发现单篇文献同时公开：

1. 变更对象是一个当前运行中的分布式应用参与者图，而非单设备状态、静态组件依赖或浏览器扩展包；
2. 在候选图边可承载业务载荷之前拦截变化，并原子冻结旧 Epoch 数据平面；
3. 冻结时仍保留受类型、大小、速率和语义限制的证明/授权控制平面；
4. 用多维隐私保障偏序判断“非下降”“下降”或“不可比”，而不是只比较是否变化或单一风险分；
5. 非下降自动提交，下降或不可比才征求用户授权；
6. 授权对象绑定候选图根、Epoch、具体降级维度、数据类别和策略版本；
7. 新密钥或能力只在提交新图 Epoch 后发放，旧能力和在途消息不能跨 Epoch 使用；
8. 整个迁移满足可验证的线性化与崩溃恢复不变量。

这就是目前可申请性的主要根据。

### 2. 仍然存在明显的组合启示风险

审查员可能把以下资料组合：

- 用 Gapfruit 或 Intel 的组件/证明图作为图基础；
- 用 Cisco 的状态变化后重新准入作为重新评估机制；
- 用 Chrome 或 Microsoft 的权限变化后停用、提示和同意缓存失效作为用户授权机制；
- 用 Fortanix、RATS 或证明后密钥释放技术作为通信准入；
- 用传统 Epoch 租约作为旧状态失效和新状态换发机制。

因此，仅把这些步骤依次列出仍可能被认为显而易见。需要在说明书和权利要求中证明它们存在**功能上的相互作用**：

- 图 Epoch 不是普通版本号，而是数据平面闸门、能力、密钥、用户授权和证明新鲜度的共同域；
- 冻结不是普通“停用应用”，而是严格区分业务数据平面与不可承载业务数据的控制平面；
- 降级比较直接决定分布式迁移走自动提交还是候选图绑定授权分支；
- 原子顺序解决了普通“先变化、后扫描”无法解决的 TOCTOU 数据泄漏；
- 崩溃恢复协议保证不能同时恢复旧图和新图的数据能力。

如果这些细节没有设计和实验支撑，创造性风险仍为中高。

## 六、权利要求布局建议

### 1. 主申请

建议围绕同一发明构思布局：

- 方法独立权利要求；
- 系统独立权利要求；
- 计算设备独立权利要求；
- 计算机可读存储介质权利要求。

系统实施例可包括：

- 图变更拦截器；
- 隐私状态协调器；
- 数据平面闸门；
- 控制平面网关；
- 证明收集器与验证器；
- 策略及偏序比较器；
- 密钥或能力租约代理；
- 授权控制器；
- Epoch 提交和崩溃恢复模块。

### 2. 从属权利要求

可覆盖：

- Application Instance 的具体构成；
- 图根、证据根、策略摘要和撤销 Epoch；
- WASM 声明能力和实际授予能力的交集；
- Native workload 默认为未知，除非具有可验证隔离证据；
- CPU 与 GPU/NPU 的组合证明；
- LLM 或加速器服务的日志出口、保留策略和密钥释放条件；
- 证明过期、撤销、程序摘要变化、Host 配置变化触发同一迁移事务；
- 强连通分量、循环图和图规模上限；
- 控制消息白名单、字段模式、最大长度、速率和总量约束；
- 用户授权与组织授权的优先级；
- 硬性下限不可被用户覆盖；
- 可信隐私域对子图证据作作用域受限的汇总；
- 绿、黄、冻结和重新评估的界面状态。

### 3. 不宜放在主独立权利要求中心的内容

- 绿标或黄标的颜色；
- “所有 Actor 的最弱项决定整体”这一抽象规则；
- 单纯使用 WASM、TEE、Confidential Computing 或端到端加密；
- 单纯生成 Merkle 图根；
- 单纯使用远程证明后释放密钥；
- 单纯在权限增加时弹窗；
- `actr://` URI、Tab 与 Service 1:1 等产品模型。

这些内容可作为实施例、从属权利要求，或另行评估 GUI 外观设计保护。

## 七、说明书在申请前必须补齐的技术内容

当前产品文档已经给出了正确方向，但正式申请前至少要形成以下可实施材料。

### 1. 并发和原子性

- 图变化的线性化点是什么；
- 谁先看到变更，谁有权冻结所有业务边；
- 在途消息如何处理；
- 多个并发图变化如何合并、排队或取消；
- 分区、超时、协调器崩溃和重复提交如何恢复；
- 是否需要单协调器、日志复制、共识或幂等事务编号。

### 2. 数据平面执行

- 每个发送端、接收端、Relay、TURN、Gateway 和 Host 在何处检查 Epoch；
- 旧 Epoch 密文、重放消息、延迟消息和缓存数据如何拒绝；
- 候选 Actor 在评估前是否能取得任何可解密业务数据；
- 密钥派生、换钥、能力签发和撤销的具体顺序。

### 3. 控制平面不成为旁路

- 允许的消息类型和字段；
- 明确禁止的业务载荷类型；
- 长度、频率、总量、压缩和分片限制；
- 未知字段、扩展字段和加密字段的处理；
- 防止把用户数据编码进证明 Nonce、日志或自由文本字段的规则。

### 4. 保障向量与偏序

- 至少定义身份、代码来源、运行约束、计算机密性、通信、存储、出口/日志和输出处理等维度；
- 每个维度的值域和“更强/相同/更弱/不可比”关系；
- 缺失证据、未知 Native workload 和过期证据如何映射；
- 哪些是用户可覆盖降级，哪些是硬性下限；
- 局部 Actor 变化怎样增量计算全图结论。

### 5. 实验和反例

建议实现并记录至少以下实验：

- 在候选边建立和冻结并发发生时，证明候选端收到的业务数据为零；
- 旧 Epoch 能力和授权重放失败；
- 评估期间控制平面仍能完成证明和授权；
- 控制平面无法传递超过约束的业务载荷；
- 崩溃恢复后只存在一个活动数据 Epoch；
- 同等或更强图自动恢复，降级图稳定停留在待授权状态；
- 与“先重构图、后扫描”的普通实现比较泄漏窗口。

可量化或反直觉的效果会显著改善创造性论证。

## 八、专利适格性与法域注意

中国专利法第二十二条要求发明具备新颖性、创造性和实用性，参见[国家知识产权局公布的专利法文本](https://english.cnipa.gov.cn/art/2022/10/13/art_3068_179273.html)。

2026 年起施行的新版《专利审查指南》强调：

- 创造性应针对权利要求限定的技术方案整体评价；
- 对技术问题有贡献的特征应写入权利要求；
- 算法或规则与技术特征在功能上相互支持并产生技术效果时，应考虑其贡献。

参见[国家知识产权局第 84 号令](https://www.cnipa.gov.cn/art/2025/11/13/art_99_202568.html)。

因此，本方案在中国具备成为专利保护客体的良好基础，但权利要求必须落到网络消息、数据平面闸门、密码学能力、Epoch 状态和原子提交，而不能只写“评估隐私并展示标记”。

欧洲也通常要求软件产生进一步技术效果；网络安全、密码控制和计算机内部运行控制比纯信息展示更容易满足技术性要求，参见[EPO Guidelines G-II 3.6.1](https://www.epo.org/en/legal/guidelines-epc/2025/g_ii_3_6_1.html)。

美国还需同时考虑抽象概念适格性、显而易见性和说明书充分公开。把发明具体限定为改进分布式网络安全和密钥/能力状态管理，比“计算一个安全等级”稳健。

## 十、自由实施（FTO）风险

“自己的专利可以授权”不等于“产品可以自由实施”。一个较窄的改进专利仍可能落入他人的基础专利。

正式 FTO 至少应逐项比对：

1. EP4182826B1 及其 US/PCT 同族：组件依赖图、图哈希和状态证明；
2. US11399013B2 及同族：安全服务网格、服务实例证明和会话通信；
3. US20230274034A1 及后续授权/同族：应用多维证明图；
4. US9436820B1：状态变化后的网络准入和访问控制；
5. 与证明后密钥释放、Confidential Computing 服务网格和连续完整性验证相关的有效专利。

FTO 必须按目标国家、有效权利要求和计划实现逐项进行，不能只读摘要。
