SECTION 00 · OVERVIEW

Keel Host 能力指南HOST CAPABILITIES FOR GUEST DEVELOPERS

Keel Host 能力是 Guest 沙箱与受信 Host 之间的受控边界。Guest 通过 host:* 模块的 named import 获取方法，由 Host 完成边界校验、能力授权、原生桥接和 Service 传输。本文仅面向 Guest 开发者，介绍当前支持的能力及其调用、声明和调试方式。

文档版本：V1

整理日期：2026-11-24。适用于 keel.guest/1、actr-package/2 和 capability schemaVersion = 1。本文只列出当前支持的 Guest 能力；未列出的模块和方法不属于本文范围。

使用原则

按目录导入
只使用能力目录中的模块与 named exports，并遵循固定路由 Service 的模块形式。
声明所需能力
构建 capability manifest，并在 package 中填写对应的 required-capabilities。
处理运行条件
处理权限拒绝、原生能力不可用、Service 未附着和订阅清理等运行状态。

SECTION 01 · CAPABILITY CATALOG

能力目录IMPLEMENTED GUEST-FACING MODULES

下表列出当前有真实 Host 实现、且能进入 Guest 运行时的 Guest API。“已实现”不代表任意环境下必然成功：文件选择、语音、存储和附件上传仍需要目标运行环境提供对应原生适配器，Service 还需要当前 Tab 已附着业务 Service。

Guest 模块 / 导出包能力名类型说明
host:service/<route>.callservice.callRPC固定业务路由；输入为 Base64 载荷和可选超时。
host:service/<event>.onservice.on订阅只接收指定固定事件；返回同步取消函数。
host:service.uploadAttachmentservice.attachmentUploadRPC裸 host:service 唯一允许的直接导入。
host:clipboard.writeTexthost:clipboard.writeRPC写入文本剪贴板；导出 name 与 capability name 不同。
host:local-storage.getItemhost:local-storage.getItemRPC读取字符串；不存在时返回 null。
host:local-storage.setItemhost:local-storage.setItemRPC写入字符串值。
host:local-storage.removeItemhost:local-storage.removeItemRPC删除指定 key。
host:speech.recognizehost:speech.recognizeRPC启动语音识别并返回最终文本。
host:speech.onInterimResulthost:speech.onInterimResult订阅监听识别中的临时文本。
host:speech.stophost:speech.stopRPC停止当前识别会话。
host:speech.onStateChangehost:speech.onStateChange订阅监听 recording / finalizing。
host:file-import.pickhost:file-import.pickRPC选择文件或照片，返回文件名和 Base64 内容。
统一导入规则

host:* 使用 named imports。Service RPC 和事件分别使用 host:service/<route> 与 host:service/<event> 固定模块；附件上传使用 host:service 的 uploadAttachment。

声明能力不等于授权成功

  • 构建阶段确认模块和方法存在于 contract，并生成 capability manifest。
  • 加载阶段确认方法有真实实现，且 bundle linkage、签名 manifest 和包能力声明一致。
  • 调用阶段执行相应的 capability 授权、平台权限检查及业务传输。

语音相关方法还有一层区别：导入 onInterimResult、onStateChange 或 stop 需要对应的包能力声明；真正启动原生识别会话时，由 recognize 执行 host:speech.recognize 授权。

SECTION 02 · NATIVE CAPABILITIES

原生 Host 能力CLIPBOARD · STORAGE · FILES · SPEECH

剪贴板

host:clipboard 当前只提供文本写入。Guest 导出名是 writeText，package 中申请的能力名则是 host:clipboard.write。

TypeScriptclipboard.ts
import { writeText } from 'host:clipboard';

await writeText({ text: '需要复制的文本' });

本地存储

host:local-storage 提供字符串键值读写。复杂对象需要 Guest 自行序列化；Base64、UTF-8 helper 可用于业务数据编码，但不会改变该 API 的字符串边界。

TypeScriptlocal-storage.ts
import { getItem, removeItem, setItem } from 'host:local-storage';

await setItem({
  key: 'draft',
  value: JSON.stringify({ title: '未命名', body: '草稿内容' }),
});

const raw = await getItem({ key: 'draft' });
const draft = raw === null ? null : JSON.parse(raw);

await removeItem({ key: 'old-draft' });
边界当前限制
keyUTF-8 编码后最多 1024 字节。
value字符串，UTF-8 编码后最多 64 KiB。
读取缺失 key返回 null。
原生分区参数Host 调用原生桥时携带 tabId 和 documentId；缺少桥或 documentId 时能力不可用。

文件导入

host:file-import.pick 调用原生选择器，返回文件内容而非附件 ID。需要发给 Service 时，应再调用固定附件上传或按业务协议编码。

TypeScriptfile-import.ts
import { pick } from 'host:file-import';

const { files } = await pick({
  source: 'files',
  multiple: false,
});

for (const file of files) {
  // file.name: string
  // file.base64: RFC 4648 Base64 内容
}
  • source：可选，files 或 photos。
  • accept：可选字符串数组，传递给 Host 文件选择器。
  • multiple：可选布尔值；输出统一为 files 数组。

语音识别

host:speech 支持最终识别结果、临时结果、状态订阅和主动停止。省略 continuous 表示单次语句识别；当前 Host 同时只允许一个识别会话。

TypeScriptspeech.ts
import {
  onInterimResult,
  onStateChange,
  recognize,
  stop,
} from 'host:speech';

const offInterim = onInterimResult(({ text }) => {
  // 更新识别中的临时文本。
});
const offState = onStateChange(({ state }) => {
  // state: 'recording' | 'finalizing'
});

try {
  const { text } = await recognize({ locale: 'zh-CN' });
  // 使用最终识别文本。
} finally {
  offInterim();
  offState();
}

// 在“结束录音”按钮的处理器中调用：
// await stop();
原生可用性需要单独处理

语音识别依赖原生识别桥、系统权限及设备能力。即使包声明和会话授权通过，运行环境未提供原生桥时仍会失败。订阅函数只负责移除对应监听器，不会替代 stop()，也不会自动完成最终识别结果处理。

SECTION 03 · FIXED ROUTE SERVICE

固定路由 ServiceRPC · EVENTS · ATTACHMENTS

Service 是 Guest 与当前业务 Actor 通信的主要能力。构建过程将每个 RPC 或事件编译为固定模块。Service target 由 Host 根据当前 Tab 的 Attach 状态确定，Guest 不提供 ActorId。

固定路由 RPC

TypeScriptservice-call.ts
import { call as listNotes } from 'host:service/notes.NoteService.List';
import { decodeListNotesResponse, encodeListNotesRequest } from './notes-wire';

const output = await listNotes({
  payloadBase64: encodeListNotesRequest({ limit: 20 }),
  timeoutMs: 8_000,
});

const notes = decodeListNotesResponse(output.payloadBase64);
Guest 输入不包含 route

固定模块的公共输入是 { payloadBase64, timeoutMs? }。Host 在适配层注入模块名对应的 route，再执行内部 host:service.call 边界校验和 service.call 授权。内部 wire contract 中的 { route, payloadBase64, timeoutMs? } 不应照抄为 Guest 公共参数。

  • 路由名必须是至少两段的点分名称，例如 notes.NoteService.List。
  • 每段以字母或下划线开头，后续可含字母、数字、下划线或连字符；完整名称最长 256 字符。
  • host:service/ 后不能再用 / 分隔业务 Service 与方法。
  • 默认超时为 30 秒；显式值必须大于 0 且不超过 300000 毫秒。应用可以选择更短超时。

固定事件订阅

TypeScriptnote-events.ts
import { useEffect } from 'react';
import { on as onNoteEvent }
  from 'host:service/notes.NoteEvent';

useEffect(() => {
  return onNoteEvent(({ event, payloadBase64 }) => {
    // event 与固定模块名一致；按业务 proto 解码 payloadBase64。
  });
}, []);

on 返回同步清理函数，应作为 React effect cleanup 或在组件销毁时调用。Host 先过滤固定事件，再交给 Guest handler；权限撤销、Tab 拆除或 Engine reload 时也会关闭关联传输。

固定附件上传

TypeScriptattachment.ts
import { pick } from 'host:file-import';
import { uploadAttachment } from 'host:service';

const { files } = await pick({ source: 'files', multiple: false });
if (files.length > 0) {
  const receipt = await uploadAttachment({
    filename: files[0].name,
    base64: files[0].base64,
    type: 'document',
  });
  // receipt.attachmentId 可放入后续业务 RPC 的 proto 消息。
}
字段 / 行为约定
filename非空文件名。
base64严格 RFC 4648 padded Base64；解码后最多 7 MiB。
typeimage / document / audio / video / other；默认 document。
id可选的调用方附件 ID；省略时由 Host 生成。
传输由 Host 原生 prepare / chunk / result 流程完成，需要当前运行环境提供附件上传桥。

类型声明与业务编码

固定模块名由应用定义，通常需要应用侧提供 .d.ts。proto 描述业务 route 和消息结构，Keel contract 描述 Host/Guest 边界；两者都不能由 TypeScript 泛型或 actr gen 自动替代。

查看固定路由声明示例
TypeScripthost-service.d.ts
declare module 'host:service/notes.NoteService.List' {
  export function call(input: {
    payloadBase64: string;
    timeoutMs?: number;
  }): Promise<{ payloadBase64: string }>;
}

declare module 'host:service/notes.NoteEvent' {
  export function on(
    handler: (event: { event: string; payloadBase64: string }) => void
  ): () => void;
}
SECTION 04 · DECLARATION & PACKAGE

能力声明与打包LINKAGE · MANIFEST · REQUIRED CAPABILITIES

Host 能力涉及两份不同产物：编译器生成的 capability manifest描述 Guest 实际链接的能力；package manifest 的 required-capabilities描述应用向 Host 申请的权限。两者都由签名包保护，但用途不能互换。

产物生成 / 编写方式核心用途
workload/capabilities.json--v1-capability-manifest 生成记录 imports、Host RPC/事件和组件；加载时与 bundle linkage 重建结果比对。
front-package.toml应用维护声明 workload、所需 Front capabilities、Service dependency、签名和文件条目。

生成 capability manifest

Bashbuild-guest.sh
bun /path/to/actrium/packages/keel/src/cli/bin.ts build src/guest.tsx \
  --outfile workload/guest.js \
  --contract src/keel.contract.ts \
  --v1-capability-manifest workload/capabilities.json \
  --no-minify
JSONworkload/capabilities.json（结构示例）
{
  "schemaVersion": 1,
  "keelApi": "1.0",
  "guestEntry": "workload/guest.js",
  "imports": ["host:clipboard", "host:service"],
  "hostModules": {
    "clipboard": {
      "rpc": ["writeText"]
    },
    "service": {
      "rpc": ["notes.NoteService.List"]
    }
  },
  "components": ["Button", "Text", "View"]
}

固定 Service 模块在 manifest 中归入 hostModules.service：RPC 记录固定 route，事件记录固定 event name。Image 等源码组件名还可能按协议映射为其他 manifest 名称；Host 能力目录不应直接照抄源码模块别名。

声明 package 能力和 Service dependency

TOMLfront-package.toml（节选）
format = "actr-package/2"

[workload]
profile = "keel.guest/1"
entry = "workload/guest.js"

[workload.keel]
runtime = "js"
guest-api = "keel.guest/1"
capabilities = "workload/capabilities.json"

[host]
profile = "actr.host/1"
api = "^1.0.0"
required-capabilities = [
  "service.call",
  "service.on",
  "service.attachmentUpload",
  "host:clipboard.write",
  "host:file-import.pick"
]

[dependencies.service]
actor = "publisher.example.com/example-service"
version = "=0.1.0"
contract = "proto/example.proto"
required = true

[[files]]
path = "workload/capabilities.json"
role = "profile"
media-type = "application/json"

实际打包文件条目还需包含正确的 size 和 sha256；请使用 actr pkg pack 生成并签名，再用 actr pkg verify 验证，不要手填全零摘要后作为正式包发布。

能力命名注意事项

新包推荐按照能力目录填写方法级能力名，并只声明实际使用的能力。特别注意名称差异：Guest 导出的 writeText 对应 package 中的 host:clipboard.write。固定 Service RPC、事件和附件上传分别声明 service.call、service.on 和 service.attachmentUpload。

SECTION 05 · AUTHORIZATION & SECURITY

授权与安全模型FAIL CLOSED AT LOAD AND CALL TIME

加载前：校验 Guest 链接与包声明

  1. 从 guest.js 首行读取 bundle linkage，不执行 Guest 业务代码。
  2. 根据 Host contract 重建 capability manifest，并检查导入的模块和方法是否受当前版本支持。
  3. 将重建结果与包内签名的 capabilities.json 比较；数组顺序不影响比较，但缺失、额外字段或条目差异会导致失败。
  4. 检查 manifest 中的能力是否已包含在 package 声明中。
  5. 只把验证通过的模块和方法绑定到新的 Keel Engine。

调用时：Schema、授权和传输缺一不可

能力生效条件演示

点击各项可模拟缺失条件。此交互用于解释模型，不读取真实包或设备状态。

●使用能力目录模块与方法属于当前版本
●linkage 与 manifest 一致构建产物未被替换或篡改
●package 已声明required-capabilities 覆盖导入方法
●策略与会话允许grant、OS 权限和 session 快照通过
●执行目标可用原生桥存在，或 Service 已 Attach
条件完整：调用可以进入业务边界与传输阶段

运行时授权快照

Actrium authorizer 综合包声明、逐项 grant 状态、平台 OS 权限和 session.allowedCapabilities。Service 事件在打开原生或 HTTP 传输前授权，并监听能力撤销；撤销后执行清理。授权不是一次性构建标签，而是运行时可以变化的约束。

边界校验

  • parseInput 校验 Guest 输入，parseOutput 校验 Host 返回，parseEvent 校验订阅事件。
  • rpc<Input, Output> 的泛型只提供 TypeScript 类型，不会自动生成上述运行时校验。
  • Base64 是编码，不是加密、签名或内容安全审查；业务 proto 消息仍需由 Service 验证。
  • 固定 route 会由 Host 覆写注入，Guest 不能通过额外 route 字段改变目标。
Service 权限粒度

固定路由用于确定业务 RPC 或事件目标，package 仍需声明对应的方法级能力：service.call、service.on 或 service.attachmentUpload。权限拒绝时，应同时检查这些声明和当前会话授权。

SECTION 06 · LIFECYCLE & DEBUGGING

生命周期与调试SUBSCRIPTION CLEANUP AND FAILURE TRIAGE

订阅与销毁

1
创建订阅
检查声明、授权与事件源
→
2
返回 cleanup
同步句柄，可取消 pending 授权
→
3
接收事件
Schema 校验与固定事件过滤
→
4
撤销 / teardown
停止传输、移除监听与跟踪记录
  • React 中使用 useEffect 时，直接返回 on 的取消函数。
  • 语音的 onInterimResult 和 onStateChange 只移除对应 listener；识别停止由 stop 或原生会话结束控制。
  • Service 事件 handler 抛错会被 Host 记录，不应依赖 handler 异常来关闭传输。
  • 权限撤销、Engine reload 和 Tab teardown 都应被视为正常清理路径，而不是只在组件卸载时处理。

常见失败定位

现象 / 错误优先检查
unknown_capability对照能力目录检查模块名、导出名和固定路由拼写。
capability_mismatch重新生成 bundle 和 capability manifest；检查固定 route、guestEntry、签名包内 profile 是否一致。
提示未声明 service capability检查 [host].required-capabilities 及 [dependencies.service]，不要只检查 TypeScript import。
权限拒绝或 permission_restricted 类错误检查包声明、用户 grant、OS 权限和当前 session allowedCapabilities。
原生模块 unavailable检查当前平台是否注入存储、文件选择、语音或附件原生桥；已实现不等于桥必然存在。
Service event source unavailable检查当前 Tab 的 Service Attach 和事件传输端点。
Service call timed out检查默认 30 秒或应用自定义超时、Service handler 和传输；最大边界为 300 秒。
Speech recognition already in progress结束或停止当前识别会话后再启动新的 recognize。

调用失败排查顺序

  1. 确认使用 named import 和准确的模块 / 固定路由名。
  2. 用 --v1-capability-manifest 重新生成 workload/capabilities.json。
  3. 确认 package 的方法级 required-capabilities 覆盖所有导入方法。
  4. 确认包签名和 profile 文件条目来自同一次构建。
  5. 确认权限快照、原生桥和 Service Attach 状态。
  6. 最后检查业务 Base64 / Protobuf 编解码、超时和 Service 返回错误。
SECTION 07 · RELEASE CHECKLIST

发布检查GUEST RELEASE CHECKLIST

完成能力接入后，请从模块导入、能力声明、包签名和运行状态四个方面检查应用，确保构建产物与目标设备上的实际行为一致。

在目标设备验证原生体验

本地存储、文件导入和语音识别应在目标设备上验证原生桥、系统权限和异常状态，同时检查 Service 连接、权限拒绝和订阅清理。

发布前检查清单

  1. 所有 host:* 导入均来自本文能力目录，并使用 named exports。
  2. 固定 Service route 和 event name 与业务 proto、类型声明保持一致。
  3. 使用 --v1-capability-manifest 重新生成 workload/capabilities.json。
  4. [host].required-capabilities 覆盖实际使用的方法，且名称与能力目录一致。
  5. workload/capabilities.json 以 role = "profile" 纳入签名包，并与 bundle 来自同一次构建。
  6. 已验证权限允许与拒绝、原生桥不可用、Service 未附着、超时和订阅清理路径。
