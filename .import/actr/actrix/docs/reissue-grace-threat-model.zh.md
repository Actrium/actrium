# `/ais/reissue` 30 天过期证明宽限期 —— 威胁模型与安全评审

## 背景

节点通过一次性注册（`POST /ais/register`）拿到身份 `ActrId` 与一组凭证，之后靠 renewal token（续期令牌）走 `POST /ais/renew` 软续期。当续期令牌本身已经失效（例如节点长时间离线、超过续期令牌 TTL），软续期不再可用，此时的兜底路径是 `POST /ais/reissue`：**在不分配新序列号的前提下，为既有的稳定身份重新签发凭证**。

`/reissue` 的持有证明（possession proof）是节点最后一次拿到的 renewal token。为了让「长时间离线」的节点仍能找回自己的稳定身份，AIS 对这份证明放宽了时效：

```
// actrix/crates/ais/src/renewal.rs
pub const REISSUE_BINDING_GRACE_SECS: i64 = 30 * 86_400; // 30 天
```

也就是说：一份 renewal token 即使已经**过期**，只要过期时间在 30 天以内，它对 `/reissue` 仍然是有效的持有证明（但对 `/renew` 无效——续期仍然要求未过期令牌）。超过 30 天后，绑定记录被垃圾回收（`gc_expired_tokens`），该身份不再能被 reissue，节点只能重新注册一个全新的序列号。

本文档回答评审提出的安全签署要求：**为什么接受一份最长过期 30 天的持有证明是可以接受的，它打开了多大的攻击面，以及有哪些边界与缓解措施把风险约束在可接受范围内。**

## 一、为什么需要这个宽限期

- 续期令牌 TTL 通常只有 1 天（`renewal_token_ttl_secs` 默认 86400）。没有宽限期，一个离线超过 1 天的节点就永久失去了「凭稳定身份恢复」的能力，只能改用新序列号——这会打断所有依赖该 `ActrId` 的 ACL、路由、粘性会话与业务状态。
- reissue 存在的唯一目的就是服务这些「离线过久、续期令牌已失效」的节点。宽限期是这条恢复路径的时间窗口。

## 二、攻击面：宽限期到底放大了什么

核心风险：**一份被泄露的旧 renewal token，其「恢复权限」被延长了最多 30 天。**

具体来说，如果攻击者拿到了某节点已经过期（但过期不足 30 天）的 renewal token，并且**同时**满足注册认证，就可能凭这份旧令牌为该 `ActrId` 重新签发一份可用凭证，从而以该身份接入。没有宽限期时，一份过期 1 天以上的令牌就已经作废；有了宽限期，这份旧令牌的可利用窗口被拉长到 30 天。

注意这里的关键限定词是「同时满足注册认证」——见下节的边界分析。

## 三、把风险约束在可接受范围内的边界与缓解

1. **reissue 不是「只凭令牌」就能通过。** `/reissue` 仍然要求完整的注册认证（`verify_registration_identity`）：
   - 包注册（Package）需要制造商签名证明（manufacturer proof），且原 nonce 已被首次注册消费、必须重新签名，无法重放；
   - 源关联注册（Linked）需要 realm secret。

   也就是说，**单靠一份泄露的旧 renewal token 不足以完成 reissue**——攻击者还必须突破注册层认证。宽限期放大的是「令牌 + 注册认证同时被攻破」这一复合条件下的时间窗口，而不是单一令牌的独立权限。

2. **持有证明按序列号逐一绑定（per-actor binding）。** 证明的哈希必须匹配 AIS 为**这个确切 `ActrId`** 记录的绑定（`find_binding_token_expiry(actor_id, hash)`）。因此一份证明只能恢复它自己对应的那一个序列号，**不能**跨 actor 铸造凭证、也不能为任意序列号签发（缺失/未知/不匹配的证明一律拒绝）。这把「一次泄露」的影响面限制在单个身份，而非整个 realm 或同类型的其他 actor。

3. **宽限期是有界的，且到期即回收。** 超过 30 天，绑定记录被 `gc_expired_tokens` 删除，身份不再可 reissue。攻击窗口不会无限累积。

4. **只恢复稳定身份，从不铸造新序列号。** reissue 契约上是 stable-identity：响应的 `ActrId` 必须与请求一致，客户端侧也再次校验。它不能被用来批量申请新身份。

5. **续期权限没有被一起放宽。** 宽限期只作用于 `/reissue` 的持有证明判定；`/renew` 仍然要求未过期令牌。换言之，旧令牌不能拿去做常规续期，只能走「认证 + 恢复」这条更重的路径。

6. **令牌只以哈希存储、从不落日志。** 数据库只保存 `SHA-256(token)`，日志层禁止输出令牌、令牌哈希与 realm secret。即使数据库被读取，也拿不到可直接使用的令牌明文。

7. **本次 PR 收紧了失败分类。** possession 失败与 realm 拒绝在协议层用不同的错误码区分（possession 失败使用 `REISSUE_POSSESSION_NOT_PROVEN_CODE`，realm 拒绝保留 `403`）：一次过期/未知的持有证明不会被误判为「realm 永久拒绝」而终止恢复，也不会把一次身份问题伪装成 realm 层决策。这让「宽限期外/证明不匹配」的失败路径行为明确、可观测（见 warn 级别 `membership_identity_loss` 日志）。

## 四、残余风险与建议

- **残余风险：** 在「注册认证凭据 + 过期不足 30 天的 renewal token」被同时窃取的复合场景下，攻击者可在最长 30 天窗口内以该身份重新接入。这属于「凭证 + 认证双重泄露」量级的风险，其影响被逐序列号绑定限制在单个身份。
- **建议（后续工作，非本 PR 阻塞项）：**
  1. 将宽限期做成**可配置**（按部署的安全等级调节，甚至可设为 0 关闭），而非固定 30 天硬编码；
  2. 探索把恢复绑定到**更强的设备侧证明**（device-held key / 硬件密钥），使「仅泄露旧令牌」在任何窗口内都不足以恢复；
  3. 为 reissue 成功事件补充审计日志与告警，便于检测异常恢复。

## 五、签署请求

本机制在「宽限期有界（30 天）、逐序列号绑定、reissue 仍需注册认证、续期权限未放宽、令牌仅哈希存储」这一组边界下，将风险约束为「需要复合泄露、且仅影响单个身份、且时间有界」。请安全评审据此判断是否接受当前默认值，或要求将宽限期配置化 / 绑定更强证明后再合入。
