# Actro 产品标记与交互

本章只规定 Actro 如何把通用模型呈现给用户，不给通用 Actor 图增加根、终端或 Edge 特例。

成熟度：`Specified`。

## 1. Tab 定位的是图，不是前台自己

每个 Tab 通常绑定一个 Front Actor。Front Actor 是产品入口，不是安全根。

Actro 必须从它出发找到所属的完整无根应用图，显示该图当前 `ApplicationAssurance`，而不是只显示前台节点。依赖当前断线、空闲或没有任务，不能把它移出图。多个 Tab 落到同一连通图时，显示同一份应用状态。图结构变化后停止沿用旧状态。

Tab 可以提供逐层查看 Actor、效果、目标、证据和依据的导航，但不改变底层计算。

Actro Tab 若以 Native Actor 承载固定 Rill Host 加用户可编写的 Rill Guest，最终有效能力声明必须覆盖整个 Tab 进程。Host 能做而 Guest 不能做的出口，仍是这个 Actor 的出口。不能只评估 Guest。

## 2. 三色

**绿色**  
当前就绪切面上：图合法，所用 Actor 通道有效，每个节点都有适用保障，每个不能排除的 `Transfer` 都确认受控，并且确认不存在 `Retain`。它是这次核对里指针一致、全部成员 `ACTIVE` 时的可验证结论，不是应用名称的永久认证，也不表示所有 Actor 内部状态曾在同一物理瞬间同时如此。

「确认不存在 `Retain`」是有意的硬立场：绿色只适用于**纯瞬态处理**——Actor 自身在使用边界结束后不保留任何可恢复的应用信息。合法持久化必须走用户认可的输出边界（如受信 Workspace）；数据一旦进入受信非 Actor 目标，即离开本应用图的保障范围，其后续保留与再流出由该目标自身的信任关系承担。交互上必须把这层边界讲清楚，不得暗示绿色覆盖已写出的数据。

**黄色**  
得到绿色所必需的事实里，至少一项无法确认，同时没有已确认的未受控泄漏能力。常见来源：无法排除 Native 旁路、证明过期、厂商证据覆盖不到某条日志路径、目标是否可信尚无规则、验证者不被当前策略识别。

**红色**  
已确认存在至少一项未受控泄漏能力。例如明文日志已启用、可向任意互联网地址发送、临时使用结束后仍可恢复明文、管理员已确认能读运行中明文且用户不把该边界当可信输出。

图无效、通道建不起来、快照无法闭合，或任一图成员仍处于保障挂起时，显示「安全状态无法建立 / 正在重新验证 / 通信已阻断」。不要把它画成可接受的第四色，也不要把挂起中的应用显示成绿色。

## 3. 用户改的是规则，不是颜色

用户不能把某个应用点成绿色。用户配置的是可识别行为模式的可信 / 不可信规则，例如：

- 允许当前本地 Front Actor 输出到本机主屏幕；
- 信任某个准确 Workspace 路径；
- 不信任任意互联网通配出口；
- 在明确范围内接受某个 Actor 主体；
- 信任某个验证者核验特定类型的 TEE 证据。同一评定上下文若有多份均被接受的结论，系统取最弱项，用户不能挑选较绿的验证者。

系统用「当前技术事实 + 当前证据 + 当前规则」重新计算颜色。行为无法被可靠识别，就不能命中可信规则，相关事实保持黄；已确认属于不可信模式，则为红。

普通用户的主要选择在 Actor 层：信不信这个主体、这个实例、这类可识别出口，以及要不要在当前黄 / 红下继续跑。发布根、厂商证明根、验证者根放在高级设置。默认值可以内置，但必须能查看、增删和撤销。深层根一变，相应保障必须重算。

## 4. 风险接受与输入授权

黄或红出现时，用户可以选择「接受当前显示的风险并继续」。交互必须指出是哪个 Actor、哪项能力、哪个目标，区分未知与已确认未受控，写明范围，并记录所依据的状态根和策略版本。不要使用「仍然安全」这类措辞。范围扩大或事实变化后，不得静默复用。用户随时可撤销。

接受之后，黄仍是黄，红仍是红。

摄像头、麦克风、文件选择、剪贴板是另一套交互：

- 输入开关回答「要不要把数据交给应用」；
- 颜色回答「应用拿到数据之后，出口是否受控」。

输入开关变化通常不改颜色。Actor、能力、宿主、证据、信任规则或图结构变化才触发保障重算。

## 5. 状态变化时怎么显示

Actor 状态一变，立即停止把旧 `ApplicationAssurance` 当作当前事实。变化 Actor 显示为「保障挂起 / 正在重新验证」，并禁止受影响的数据处理和输出。

重算完成后：颜色不变或变强，可以自动恢复；变黄或变红，保持阻断并解释原因；通道无效，不提供风险接受绕过。用户不必为每次证据刷新点确认，只要验证者、作用范围和策略没变。

整图旧结论失效时，未变化且不依赖变化节点的 Actor 可以继续自身工作，但顶层不能继续显示旧绿色，也不能用「子图绿色」暗示完整应用仍受保障。无法判断是否依赖时，必须停。

能力或配置变化后重新变绿，只约束新产生或新接收的数据按新声明流动。变化前已持有的数据受「取得时声明 ∩ 当前声明」约束，不能走新开的出口，也不能再用已删除的旧出口。

## 6. 三层解释

1. **一眼可懂**：颜色、一句话含义、是否允许运行、最近变化。
2. **具体原因**：哪个 Actor、是 `Transfer` 还是 `Retain`、目标是什么、未知还是确认未受控、缺哪项证据或规则。配置变化后，须能说明旧数据仍受取得世代约束。
3. **可审计材料**：状态根、软件包 / 配置 / 能力 / 环境指纹、Assurance 对象、所信验证者（若有多份则展示最弱项，不提供挑选）、规则、信任根、有效期、成员证明、风险接受记录。

高级材料可以放深层页面，但不能让用户拿不到。

Host 应提供真实内容采样，帮助核对开发者说明。用户或其选择的代理可以查看采样、报告不符、调整实例或主体信任。这些是补充治理，不改核心技术事实。一次实例作弊，默认只打到该实例。

## 7. 强制要求

| ID | 要求 |
| --- | --- |
| `ACTRO-SEC-UX-001` | Tab 显示 Front Actor 所属完整应用图的当前保障 |
| `ACTRO-SEC-UX-002` | Front Actor 只做产品定位，不做通用图根 |
| `ACTRO-SEC-UX-003` | 顶层只用本章定义的绿 / 黄 / 红 |
| `ACTRO-SEC-UX-004` | 风险接受不改颜色 |
| `ACTRO-SEC-UX-005` | 用户配置行为规则，不能直接覆盖计算结果 |
| `ACTRO-SEC-UX-006` | 无法识别的行为不得命中可信规则 |
| `ACTRO-SEC-UX-007` | 输入授权与隐私标记分开呈现 |
| `ACTRO-SEC-UX-008` | 结论变弱时必须解释并取得风险接受后再恢复相关工作 |
| `ACTRO-SEC-UX-009` | 无效 Actr 通道不得提供用户绕过 |
| `ACTRO-SEC-UX-010` | 用户必须能查看原因、证据、作用范围并撤销信任或风险接受 |
| `ACTRO-SEC-UX-011` | 绿色只解释为当前就绪切面，不得写成「曾经存在一个全图同时世界」 |
| `ACTRO-SEC-UX-012` | 不得提供在同一评定上下文中挑选较绿验证者的交互 |
| `ACTRO-SEC-UX-013` | 配置或能力变化后，须能说明新声明只作用于新数据 |
| `ACTRO-SEC-UX-014` | 信任非 Actor 目标的交互必须呈现为「认可数据离开保障范围」，不得表述为该目标已被验证 |
